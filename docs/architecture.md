# アーキテクチャ

## 目的と境界

このリポジトリは、GB Studioを使わず、Windows上でGame Boy向けHomebrewを開発するための自己完結した作業環境である。主系統はGBDK-2020によるC開発、別系統の低レベル検証・純アセンブリ開発はRGBDSとする。初代Game Boy（DMG）互換を基準にしつつ、同じROMをGame Boy Color（GBC）でも動かせる構成を採る。

環境はリポジトリのコピーだけで再構築できることを優先する。ツール、キャッシュ、ROM、セーブデータは追跡せず、再現に必要なスクリプト、ロック情報、ソース、元アセット、設定だけをGitで管理する。管理者権限、レジストリ変更、システムまたはユーザーの恒久的な環境変数変更は行わない。

ツールの正確な版とハッシュは [`config/tools.lock.json`](../config/tools.lock.json)、エディタnpm依存は`editor/package-lock.json`を基準とする。Caravan Editorと共通STGランタイムの実装は[エディタ設計](caravan-editor-architecture.md)を参照する。STAR CARAVANは単一Cソースから作品定義＋PNGへ移行済みである。

## リポジトリの責務

```text
gb-dev/
├─ config/                 ツールの固定情報
├─ scripts/                取得、検査、ビルド、実行、清掃の実装
├─ projects/               ゲームごとの自己完結したソース
│  ├─ hello-gb/            最小のGBDK疎通確認
│  └─ star-caravan/        1ステージ制キャラバンSTG
├─ docs/                   設計、運用、デバッグ、制作規約
├─ tests/                  再利用可能なスモークテスト
├─ .vscode/                リポジトリ共有のエディター設定
├─ .tools/                 展開済みポータブルツール（追跡外）
├─ .downloads/             取得アーカイブ（追跡外）
└─ .cache/                 一時キャッシュ（追跡外）
```

- `scripts` はすべて自分自身の位置からリポジトリルートを解決する。利用者の現在ディレクトリや絶対パスに依存しない。
- `config` は再現性のための宣言を持つ。通常の `bootstrap.cmd` はロックを変更せず、更新は明示的な `-UpdateLock` に限る。
- `.tools` は `bootstrap.cmd` が公式配布物から復元する取得物であり、手編集もコミットもしない。
- `projects/<name>` は `project.json` を入口に、ソース、元アセット、生成物、ビルド出力を分離する。
- `tests` はROM生成、ヘッダー、サイズ、Git ignoreなど、GUIを必要としない検査を担当する。
- ルートの `.cmd` は安定した利用者向け入口であり、実処理を `scripts/*.ps1` に委譲する。

## データと成果物の流れ

```text
config/tools.lock.json
        │ bootstrap.cmd
        ▼
      .tools/                         （Git追跡外）

projects/<name>/assets-src/ ──変換──▶ generated/  （生成物は原則追跡外）
projects/<name>/src/ ────────────────┐
projects/<name>/include/ ────────────┼─ build.cmd ─▶ build/<configuration>/ROM
projects/<name>/project.json ────────┘                （Git追跡外）
                                                        │
                                                        ├─ test.cmd
                                                        └─ run.cmd
```

人が編集する情報は入力側に置き、生成可能なものは出力側に置く。`generated` のC/H/BINや `build` のROM、オブジェクト、マップ、シンボルを直接修正してはならない。

## ツールチェーンの分離

GBDKとRGBDSは、どちらもSM83向けコードを扱うが、アセンブリ構文、オブジェクト形式、リンカー、ランタイムの前提が同一ではない。

- GBDKプロジェクトはGBDKの `lcc` をドライバーとしてビルドする。
- GBDK内のSDCC/SDAS系アセンブリと、RGBDSのRGBASM構文を混同しない。
- RGBDSは純アセンブリの実験やハードウェア検証を独立したプロジェクトとして行う。
- RGBDSのオブジェクトをGBDKリンクへ、形式とABIを検証せず混在させない。
- 共有したい境界は、ROM内データ形式や生成済みバイナリなど、明示的に検証できる形にする。

## プロジェクト構造

標準的なプロジェクトは次の構造を持つ。

```text
projects/<name>/
├─ src/             Cまたは対象ツールチェーンのソース
├─ include/         プロジェクト内公開ヘッダー
├─ assets-src/      人が編集する画像、音楽、表データ
├─ generated/       変換により再生成するコード／バイナリ
├─ build/           構成別ビルド出力（追跡外）
├─ project.json     ビルド対象と出力の宣言
└─ README.md        操作、ルール、既知の制約
```

`hello-gb` はツールチェーンが正常に動くことを最短で確認するためのプロジェクトである。`star-caravan` はGB/GBC共通ROMのサンプルゲームで、DMG互換のゲームロジックを共有し、CGB実行時だけカラーパレットを適用する。

## `star-caravan` のゲーム構成

`star-caravan` は1ステージ、2分制のキャラバン型シューティングである。十字キーで移動、A/Bで連射、STARTでポーズ、タイトルではA/STARTで開始、SELECTでスコアボードを開く。残機は3。雑魚ウェーブの後に終盤ボスが出現し、時間切れまたはボス撃破でクリア、残機をすべて失うとゲームオーバーになる。

シーン遷移は次の責務に分ける。

```text
TITLE ── A/START ──▶ PLAY ── 全滅 ─────▶ GAME OVER
  │                    │                    │
  │                    └─ 時間切れ/ボス ─▶ CLEAR
  │                                         │
  └─ SELECT ─────────▶ SCOREBOARD ◀─────────┘
```

スコア上位5件のSRAM永続化は共通の `engine/caravan/save.c` が担当する。2スロット、世代番号、作品識別子、CRC16で検証し、書込みをランキング更新時に限定する。

## ゲームコードを拡張する際の層

サンプルはROM規模を抑えるため一部を単一翻訳単位にまとめてもよいが、機能追加時は次の境界を保つ。

- **プラットフォーム層**: GBDK API、割り込み、バンク、DMG/CGB判定を局所化する。
- **入力層**: joypadの現在値、押した瞬間、離した瞬間をフレームごとに一度だけ生成する。
- **シーン層**: タイトル、ゲーム、ポーズ、ゲームオーバー、クリア、スコアボードの遷移と寿命を管理する。
- **ゲームプレイ層**: プレイヤー、弾、敵、ボス、当たり判定、ウェーブ、得点、タイマーを管理する。
- **描画層**: 背景・ウィンドウ・スプライトの割当て、dirty更新、OAM転送を管理する。ゲームロジックがVRAMへ無秩序に書き込まないようにする。
- **サウンド層**: 効果音と曲の更新を分離し、フレーム予算を明確にする。未使用時は無音実装を許容する。
- **アセット層**: `generated` の型付きデータを公開し、変換方法やタイル番号の所有関係を隠蔽する。
- **保存層**: `engine/caravan/save.c` に集約する。書き込み許可、検証、バージョン付け、破損時の初期化を一か所に集約する。

描画、サウンド、当たり判定の内部表現は、シーンから直接ハードウェアレジスタを触らなくて済むAPIにする。割り込みとメインループの共有状態は最小限に保つ。

## フレーム更新方針

ゲームの1フレームは、概念上、次の順序で処理する。

1. 入力を一度読み、エッジ情報を作る。
2. シーンとゲームロジックを更新する。
3. 表示すべき状態を描画キューまたはシャドウOAMへ準備する。
4. VBlankに同期する。
5. VRAM/OAMへ、そのフレームの予算内で転送する。
6. 効果音・音楽ドライバーを定めた周期で更新する。

重い処理をVBlank割り込みへ詰め込まず、メインループで事前計算し、VBlank中は転送量を制御する。フレーム落ちが起きる場合は、最悪時の敵・弾数とVRAM転送量を計測してから最適化する。

## ポータビリティと依存方向

- スクリプトから外部コマンドを呼ぶときは `.tools` 内の絶対パスを使う。
- `PATH` を使う場合も `scripts/setenv.cmd` を呼んだ現在プロセス内だけに限定する。
- プロジェクトソースはホストPC固有パスを埋め込まない。
- `.tools` の内部レイアウト差は共通スクリプトで吸収し、各ゲームに探索ロジックを複製しない。
- ツール固有オプションは固定された版の公式ドキュメントまたは同梱例で確認する。
- 別PCでは追跡対象をコピーし、`bootstrap.cmd`、`doctor.cmd`、`build.cmd` の順で再構築する。
