# GBC専用バックエンドの試作と実測

対象は `touhou-kouma`。2026-09-17、既存の未コミットv27作業を保持して実施。ROMと計測値の確定情報は `projects/touhou-kouma/touhou-kouma-design/qa-v28.json` に保存する。

## 判定

GBC専用化、WRAMバンク分離、BG弾幕96発の管理枠、反転タイル辞書、SM83の描画処理を実装した。**現時点では「高速化に成功した版」とは判定しない。** 旧GBC版より軽い道中が遅くなる結果も出ているため、v28は専用設計を検証する試作版である。v27のROMを比較用に残した。60更新/秒の目標は未達成。

本編の難易度は変えていない。ボスごとの上限は12、18、22、26、30、36、40発を維持し、96発は専用負荷試験で検証する。エディターの道中BG弾幕オプションは黒背景専用で、通常背景・障害物との併用はしない。本編の道中背景は残している。

## GBC専用の実装

- `hardware: "gbc"`、ヘッダーC0、`-Wm-yC`。エディターの保存時にプロジェクトのビルド設定も同期する。ROMプレビューもCGBモードを選ぶ。専用モードは独立弾プールを必須とする。
- 通常のC変数・OAMバッファ・割り込み共有状態は固定WRAM。スタック上端をD000に指定し、下向きに固定領域内で使用する。リンカー結果を検査して最低1KiBのスタック余白を確保する。
- WRAMバンク1を敵・通常弾、バンク2をBG弾・合成作業に分離する。BG公開関数の入口と出口でSVBKを保存・復元する。弾1発ごとのバンク切替は行わない。
- 動画と大型ボスの作業領域は、同時に使わないBG合成領域と共有する。動画のタイマー割り込み中はバンク2を維持し、終了時に戻す。
- 通常弾はSoA配列、敵の攻撃予定表は13枠。OAMは論理生成と分離し、8×16 OBJをメタスプライト単位で配分する。総数40・保守的な行帯上限10を維持する。
- 大型ボスの弾合成はv27の直接索引を維持し、GBCのバンク領域に移した。大型ボスと重ねる弾数は32発のままである。

| 領域 | 用途 |
|---|---|
| 固定WRAM C000〜CFFF | 通常グローバル、割り込み、OAM、スタック |
| バンク1 D000〜 | 21アクターと通常弾の独立配列 |
| バンク2 D000〜D4DF | 最大96発のBG座標・速度・寿命・誘導情報 |
| バンク2 D500〜D97F | 32×18セルの16ビット弾配置マスク |
| バンク2 D980〜DBBF | BGタイル番号 |
| バンク2 DBC0〜DDFF | GBC属性 |
| バンク2 DE00〜DF7F | 最大24枚の合成タイル転送パケット |

通常モードの他サンプルを壊さないため、共有エディターにはdual設定を残す。東方プロジェクトの実行対象はGBCのみ。元のモノクロ画像・変換用データは破棄していない。

## タイル辞書と転送

2×2ドットを8×8タイル内の16位置に配置する。0〜3個の全697マスクを上下左右反転で正規化すると181タイルになる。2,896バイトのタイルをVRAMバンク1へ常駐し、128KiBのROM索引から番号と反転属性を引く。単独ドットは32バイトの小表から直接取得し、複数ドットだけをSM83で解決する。697マスクすべての画素復元をテストする。

4個以上が重なるセルは動的合成する。96発では最大24セルなので、24枚ずつの表裏領域を用意する。使ったセルだけを消去して再構成する。プレイヤーの局所的なBG当たり判定を維持し、実被弾を起こすC/シミュレーション照合も行った。

最初の実装は全マップ・属性72ブロックと最大24タイルを同じVBlankで転送していた。Boytaceanでは通過したが、**BGBの最大負荷試験では転送が可視走査まで超過**した。修正版は非表示側タイルを先に送り、マップ転送の開始が遅い場合は次のVBlankを待つ。両マップの完成後にのみ表示面を切り替える。密集時に追加待機が生じるので、96発を60fpsで描けるという根拠にはしない。

差分転送による全マップ送信の削減は未実装。GBCの属性を毎回送る固定費は、従来の白黒BG方式より大きい。

## 測定と失敗した仮説

実ROMの論理更新入口・公開トレース・PPUフレームを読み、通常入力だけで測定した。ゲームRAMの書換えはしない。LCD自体の約59.73Hzと、ゲームロジックの「更新/秒」を区別する。

本編比較はステージ1、射撃開始を論理更新60へ揃え、120〜1000の880区間を測る。描画方式が異なるため、旧版と新方式の画素・内部トレースの完全一致を主張しない。残機、生成落ち、OAM上限と実際の挙動を別途検査する。

最終転送修正後の本編再測定も、霊夢58.73→55.04更新/秒、魔理沙53.74→53.41更新/秒だった。RAMを増やしても、描画配分・メタスプライト処理・敵移動のCPU費用は残る。下表はゲームロジックの頻度であり、LCDの描画周期ではない。

| 条件 | 旧v27 | GBC専用v28 | 測定 |
|---|---:|---:|---|
| 本編ステージ1・霊夢 | 58.7265 | 55.0369 更新/秒 | Boytacean、880区間 |
| 本編ステージ1・魔理沙 | 53.7425 | 53.4148 更新/秒 | Boytacean、880区間 |
| 本編後半ボスの観測区間、最大28発 | 未比較 | 52.3632 更新/秒 | Boytacean、299区間、デモによる観測 |
| 敵8体＋BG96発 | 容量対象外 | 21.5234 更新/秒 | BGB、600区間 |
| 同じ96発ROM | 容量対象外 | 26.4651 更新/秒 | Boytacean、600区間 |

96発ではエミュレーター間に時間差が出た。転送のハードウェア時間を重く見るBGBの結果を保守的な指標とする。平均して都合のよい値にはしない。両者とも720更新の負荷実行とネイティブ601観測点を別々に記録している。容量上限を超える生成要求は破棄され、96発試験の生成落ち337件もQAに残す。これはフレーム落ちの回数ではない。

最大転送専用ROMでは、BGBで転送終了の最遅走査線151、通常の敵8体＋96発では152を確認した。どちらもVBlank内。最大転送専用ROMは毎更新96発を生成し直す診断であり、その更新頻度を本編の速度として使わない。

最終転送修正前の同条件の負荷試験でも、敵3体＋32発は旧高密度GBCと同程度の56.96更新/秒、敵8体＋40発は同程度の29.86更新/秒だった。これらは中間ROMとしてQAへ区別して保存する。容量拡大と速度改善は別の結果である。

最終ROMのPCサンプリングでは、本編の待機を含む時間に対しOAM計画4.56%、敵更新4.11%、複雑移動3.67%、配分判定3.61%、描画3.20%などに処理が分散した。最終96発ROMでは**弾の描画登録32.82%、移動13.80%、辞書解決1.08%**。辞書解決の負荷は途中版の6.77%から下がったが、描画登録側が主な残存ボトルネックとなっている。これらは関数呼出し計時ではなく、256〜511 T-cycle間隔のサンプリング推定で、割り込み・待機を含む。Boytaceanの転送時間の限界もあるため、BGBの実更新頻度とは分けて読む。

Cだけで作った辞書解決は敵3体＋32発で33.55更新/秒まで遅くなったため採用しなかった。SM83化、単独ドットの直接参照、OAM配分ASM、ショット対象の座標キャッシュ、空プールの省略を適用し、専用バックエンド内では改善した。それでもv27本編の速度を越えていない。

次の有力な対象は、全マップ・属性の転送削減と、弾更新から描画登録までの呼出し・座標変換の統合である。さらに容量だけを増やすことは性能対策にならない。

## 再現と検証範囲

```powershell
.\doctor.cmd
.\build.cmd touhou-kouma -Configuration Debug
.\build.cmd touhou-kouma -Configuration Release
.\test.cmd star-caravan
.tools/node/node.exe editor/tests/stg-benchmark.mjs . .cache/gbc-only/repro stress --gbc --road --more --bullets=96 --debug
.tools/node/node.exe editor/tests/gbc-barrage-extreme.mjs .cache/gbc-only/extreme-repro
# 上で作成されたROMを指定して、ネイティブ転送時刻を確認する
.tools/node/node.exe editor/tests/dense-native.acceptance.mjs ROM.gb .cache/gbc-only/native-repro
```

負荷試験は720更新のC/シミュレーション状態照合、BG弾の全画面画素比較、OAM上限の確認を含む。最大転送試験は96発を24個の4ドットセルに集め、異なる配置・空画面・表裏再利用を繰り返す専用ROM。本編の60fpsや全ステージクリアの証拠ではない。

本編の起動動画、タイトル、キャラ選択、ボム、HUD、ボスのカットインとリセットは実ROMで回帰確認する。エディターは実際のElectron UIでGBC選択、上限変更、保存後のプロジェクト読込を確認する。詳細な実施結果・失敗・使用ROMのSHA-256はQAファイルに記録する。

実機CGB、全キャンペーンの手動クリア、音の聴感確認は未実施。EmuliciousはDAPの実行結果を明記し、起動だけで検証済みとは扱わない。旧版のハイスコア保存識別子は変更しない。
