# 東方 v0.41: GBC専用実行系と性能検証

GBC専用のメモリ配置、弾データ分離、描画テンプレート、道中転送とBG弾幕の更新処理を実装した。ただし、**40発・通常プレイとも「毎表示フレームに1更新、締切超過ゼロ」の性能条件は未達**。この版は改善結果と残る問題を比較できる試作版であり、完成版として承認していない。

通常の全7面×両機体×道中／ボス開始の28経路では、旧版との状態・OAM・描画データが一致し、測定区間の更新速度もすべて改善した。40発を保持する負荷試験では密集時に大きな改善がある一方、移動弾40発の霊夢には悪化が残る。ボム継続中も性能条件を満たしていない。

## ROMと対象

- ROM: `projects/touhou-kouma/build/Release/touhou-kouma-v41.gb`
- SHA-256: `ae4f6ea7240e371b29da508724c26ef72959da05cb1e09400addc1cb37254a91`
- 4,194,304バイト。Debug／Releaseは同一バイト列、ヘッダー`$0143=$C0`。
- 基準v40: `d368acf51fd3c3f03ac8c47ddb3882991cf46bd54e5de7198e652c8c85017a23`。
- 保留中のv27/v28を一括移植していない。基準v40のエンジン、ROM、マップ、デバッグ情報と中間版を`.cache/gbc-runtime-v41/`へ保存した。
- 編集データの変更は東方の`hardware: "gbc"`のみ。画像・音楽の元データ、ゲーム内容、生成上限、得点、セーブ識別子は維持。
- 他作品は`hardware`未指定／`dual`の従来処理。star-caravanのGB/GBCビルドとROM回帰も通過。

機械可読の数値・ハッシュ・検証範囲は[qa-v41.json](../projects/touhou-kouma/touhou-kouma-design/qa-v41.json)、構造は[cgb-runtime.md](cgb-runtime.md)に記録した。

## 実装

### メモリとデータ

| WRAM | 予約バイト | 用途 |
|---|---:|---|
| 固定 | 1,478 | 共通状態、ISR、音声、shadow OAM |
| 固定スタック | 最低1,024 | `$CC00..$CFFF`、初期SP=`$D000` |
| バンク1 | 3,410 | 敵等の実体、弾SoA、論理スロット、判定・移動・アニメーションキャッシュ |
| バンク2 | 3,876 | BG弾、マスク、合成タイル、表裏マップ、使用行と変更候補行 |
| バンク3 | 2,080 | 視差タイルキャッシュと新規行の転送準備 |
| バンク4 | 779 | 動画とPCMの作業域 |
| バンク5〜7 | 0 | 未使用 |

バンクは処理単位で切り替え、元のSVBKを復元する。通常の割り込みは固定WRAMを使う。動画中はバンク4に固定し、PCM割り込みを解除してからバンク1へ戻す。リンカー結果のアドレスと固定領域の上限をビルド時に検査する。スタックは容量を確保したが、実機での最大深さの測定は未実施。

弾に25バイトの敵実体を持たせず、6バイトの識別情報と専用SoAへ分離した。39個の論理スロットと処理順は維持する。敵・ボス・演出・アイテムは21個の物理実体を共有し、従来の種類別上限で制御する。**種類ごとに完全独立した物理プールへ分割する段階までは実施していない。**

### 更新と描画

- OAMのフレーム別テンプレートをビルド時に生成し、ASMで座標を加えて出力。OAM予約・表示順と生成条件は維持。
- 区分直線経路の現在区間をキャッシュ。区間内は量子化済み速度で更新し、境界・折返し・カウンター周回では元の式へ戻す。滑らかな経路と波形、射撃設定の全面的な事前展開は未実施。
- レーザーが更新済み判定矩形を再利用。座標の原点・負座標の丸め・当たり判定サイズは変更しない。
- ボス状態・HUD値をキャッシュし、同じ値の計算と検索を削減。
- 道中の視差画像をバンク3へ常駐。新しい15列の行と変更された視差だけを準備し、VBlankのGDMAで公開。
- BG弾幕は各物理マップの現在使用行／前回使用行／HUD変更行を保持。消えた弾も更新対象になる。これは保守的な行差分であり、全セルを比較した最小差分ではない。
- 合成タイルを表裏別領域へ分離。表示中のマップが参照するタイルを更新しない。密集セルでは既存の合成マスクへ直接ORし、繰り返し分類・検索を省いた。
- 初期HUDは連続GDMA、通常のマップは変更候補行を短いASMループで転送。属性は初期設定を再利用。HBlank DMAは使用しない。

軽い場面を遅くした初期のBG差分実装とC製の行走査は不採用とした。OAMテンプレート化だけで速くなったという主張はしない。最終版でもOAM分類のCPUサンプル値は増えており、間接参照などの費用が残る。

### エディターと画像

`hardware: "dual" | "gbc"`の編集・保存・再読込と、manifestの`cgbCompatibility`／GBDKフラグを同期。GBC専用時はカラー表示を使用し、ROMプレビューとHTML出力の機種選択でDMG起動を防ぐ。未指定は従来動作。

カラー元画像とDMG元画像は保持する。専用ROMからは独立したDMG画面・画像・動画ペイロードを除き、共通フォントやHUDは残す。ROM容量はバンク境界に丸められ、最終サイズはv40と同じ4MiB。

ビルド結果へ各WRAMバンク、固定スタック、VRAM予約を追加。東方はOBJ126/128タイル、HUD27タイル、ボスBGのHUD＋辞書＋表裏合成で205タイルを予約する。ボム・カットインは既存の画像配置と復元を維持し、常駐OBJとの衝突検査を行う。

## BGB実時間測定

公開トレースのVBlankカウンターを使う。ホストPCの処理時間やPPU走査の瞬間的な位置から速度を推定しない。入力は5,000表示フレーム分の同一joypad movie。通常測定はscene=1、連続論理更新、120更新以降を対象とし、ロード・カットインは別扱い。

| 本番ROM・7面魔理沙 | v40 | v41 | v41締切超過 | p95／最大の表示フレーム間隔 |
|---|---:|---:|---:|---:|
| ボス戦 | 56.80更新/秒 | 59.10更新/秒 | 14 / 1,317 | 1 / 2 |
| 道中 | 56.39更新/秒 | 58.99更新/秒 | 35 / 2,801 | 1 / 2 |

ボス戦の観測ピークは18発。この経路だけでは40発性能を証明できない。入力SHA-256は`3399a34ccc0147084bdf92e207ea9fc13d67c593d5d431f79c20644bb6f62585`。道中は`e3c1c18e1ba015c3b160d075d23edf7ed7620157d4a9d9fc4486c51105a96830`。

道中600〜719更新の区間は約51.94更新/秒、ボス1080〜1199更新は約56.88更新/秒まで落ちる。平均59前後を性能達成とは扱わない。

最終ROMで道中のGDMA完了を1,142回観測し、最大LY149。ボスは1,499回、最大LY151。いずれもLY144〜153内で、余分なボス側VBlank待ちは0回。不正VRAM／OAM DMAアクセスのBGB停止設定を有効にした測定は完走した。これらは指定経路のエミュレーター検証であり、全状況や実機の保証ではない。

### 40発を実際に維持する試験

本番の更新・描画・音声コードをリンクし、試験用mainloopだけを差し替えた。7面ボス第1戦闘モードと自機射撃を動かし、上限40発へ不足分を補充する。600回の公開、599間隔を比較。補充・一斉生成の費用も含む。ボム中は仕様どおり0発、それ以外の公開時は40発。タイル不足による描画落ちは全条件0。

| 密集 | 魔理沙 | 38.10 | 58.65 | 11 |
| 移動 | 霊夢 | 46.65 | **45.12** | 194 |
| 移動 | 魔理沙 | 55.38 | **55.30** | 48 |
| 誘導 | 霊夢 | 32.70 | **32.67** | 496 |
| 誘導 | 魔理沙 | 39.32 | 41.36 | 266 |
| グレイズ | 霊夢 | 48.41 | 49.55 | 123 |

移動・誘導の一部で悪化している。既存の描画を保ったまま行の記録とパケットを作る費用が増えており、転送量削減だけではCPU側を埋め合わせられない。次の最適化では弾のプロット処理、マップ準備、衝突の間接参照を対象にする必要がある。

ボムの開始と終了は別集計でも長い。開始は19〜20表示フレーム、終了は21表示フレーム。**継続47更新も、霊夢94表示フレーム・魔理沙93表示フレームを消費**した。ここを除外して性能達成としない。画像セットアップ／復元と、継続中の公開処理の再設計が残る。

### CPU内訳

Boytacean 0.13.2のPCを256〜511 T-cycle間隔で決定的にサンプリング。以下は7面・魔理沙ボス120〜719更新の推定値であり、関数呼出しを計装した厳密な時間ではない。速度の判定は上のBGB測定を使う。

| 分類 | v40平均 | v41平均 | v41 p95 | v41最大 |
|---|---:|---:|---:|---:|
| 敵更新・移動 | 12,419 | 9,687 | 10,812 | 16,560 |
| 射撃生成 | 747 | 776 | 2,320 | 25,524 |
| 衝突 | 3,165 | 3,137 | 5,608 | 9,292 |
| OAM・スプライト準備 | 14,710 | 15,776 | 20,664 | 21,168 |
| BG弾更新・局所判定 | 21,668 | 22,628 | 28,984 | 40,436 |
| BG合成・マップ準備 | 11,893 | 13,680 | 15,276 | 16,328 |
| 転送関連 | 4,297 | 3,547 | 4,120 | 4,528 |
| 待機 | 49,625 | 48,490 | 69,960 | 135,456 |

分類外処理・割り込み等もQAの`other`に記録。複数の責務を持つASM関数は分割せず分類しているため、例えば`draw_shot`にはプロット用の処理も含まれる。道中と誘導40発の同じ内訳もQAに保存した。

## 同一性・回帰検証

- **本番ROM28経路**: 7面×2機体×道中／ボス開始、各1,200論理更新。座標、HP、スコア、弾・敵の存在、寿命、状態フラグ、生成落ちカウンター、OAMを照合。配列配置の違いは正規化。
- **描画比較**: VRAMから復元した160×144のBG／Window、可視OBJが参照するタイル、BG／OBJパレットを照合。28経路と40発14条件で不一致0。PPU走査位置の異なる生フレームバッファを比較した結果ではない。
- **40発14条件**: 7種類×2機体、各600論理更新で状態と描画データが一致。各fixture ROMと論理入力のハッシュも保存。
- **全7ボスの境界試験**: 最終ソースを再ビルドした診断ROMで3モード×撃破／時間切れ／混在。3599→3600更新、撃破優先、加点一度、最終モード終了を191観測で確認。弾幕・登場演出はこの診断だけ無効化しているため、通常ROMで全戦闘を通したクリアとは区別する。
- 全21モードの通常弾幕をそれぞれ最後まで通した性能・画素比較は未実施。上の1,200更新経路とモード境界診断を合わせても、その網羅確認の代わりにはしない。
- **最終本番ROM**: 両機体のHUD固定、端のOBJ制限、道中／ボスのボム画像・復元、ポーズ、カットイン中停止、ボム中・被弾中の時計継続、コンティニュー、B10切替とリセットを入力操作で確認。
- **動画**: 400フレームすべての画素照合、PCMデータ、約40秒の進行、境界でのスキップ、タイトルBGM・通常開始への復帰。フレーム超過0。
- **展示**: ロゴ→動画→タイトル→異なる面の自動プレイ→カットイン→ランキングを2周。得点を保存しないことと中断入力を確認。
- **セーブ**: v40形式のv2ランキングを両本番ROMへ読み込み、得点・世代・SRAMが一切変わらないことを確認。最新スロット破損時の旧スロット復旧も確認。旧v1の一度だけの換算、再起動、登録追加、破損／書込途中復旧は診断ROMでも確認。
- **ビルド**: doctor問題0、hello-gb clean／Debug、標準166テスト、star-caravan Debug／Release、従来GB/GBC ROM回帰4件、TypeScriptチェック通過。エディターのGBC保存／再読込は実Electron操作で確認。最後のhardware／HTML出力テスト4件も通過。

Emuliciousは途中版で起動・DAP接続できたが、数値アドレスのevaluateが`NullPointerException`となり実行確認に使えなかった。最終ROMのEmulicious合格とはしていない。GBC実機と人による聴感評価は未実施。セーブ、画像、音声の自動テストを実機確認の代わりにはしない。

## 再実行

```powershell
./build.cmd touhou-kouma -Configuration Debug
./build.cmd touhou-kouma -Configuration Release
node editor/tests/gbc-runtime-matrix.mjs .cache/gbc-runtime-v41/baseline/touhou-kouma.gb projects/touhou-kouma/build/Debug/touhou-kouma.gb .cache/gbc-runtime-v41/recheck-matrix 1200
node editor/tests/kouma-native-performance.mjs projects/touhou-kouma/build/Debug/touhou-kouma.gb .cache/gbc-runtime-v41/recheck-native --dma
node editor/tests/right-hud-rom.acceptance.mjs .cache/gbc-runtime-v41/recheck-phase-save
node editor/tests/gbc-save-compat.mjs .cache/gbc-runtime-v41/baseline/touhou-kouma.gb projects/touhou-kouma/build/Debug/touhou-kouma.gb .cache/gbc-runtime-v41/recheck-save
```

40発fixtureは`gbc-runtime-build.mjs --capture`で得た名前付きオブジェクトを使い、`gbc-runtime-stress.mjs OBJECTS OUT SCENARIO CHARACTER`で作る。v40は同スクリプトの`--baseline`を指定する。`gbc-runtime-native-load.mjs ROM OUT`でBGBの公開間隔を測る。fixture生成後のROMを本番ROMとして配布しない。

未達項目は`workflow.json`の`performance-not-met`とQAへ残した。今回の結果だけを根拠に敵数・弾数を増やしていない。
