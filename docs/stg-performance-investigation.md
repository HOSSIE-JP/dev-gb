# STG性能調査・SM83最適化（2026-09-10）

続編：[弾専用配列と更新・描画準備の統合](stg-soa-performance.md)。以下は前段階の測定記録として保持している。

計測器の追加、参考ROMの局所逆アセンブルと実行時監視、共通エンジンの最適化まで実施した。24発の同一負荷でDMGは15.76→27.52更新/秒、CGBは29.86→50.90更新/秒。敵弾上限は24→32、敵は8→12、共通オブジェクト枠は31→39へ増やした。エディターのシミュレーターにも適用している。

**密集時の60更新/秒維持と、全弾が欠けずに見える表示は未達。** 今回の32発試験では変更前の24発試験に対してDMGが高速、CGBが同等になったが、任意の素材・弾幕で処理落ちしない保証にはならない。種別上限とは別に合計OAM40個で生成を制限するため、敵12機と敵弾32発を常に同時生成できるわけでもない。

## 測定を先に固定した

比較元は作業開始時の `97954ec600bae77aeb113540be03b8ca2b546763`。GBDK 4.5.0 Windows版、Boytacean 0.13.2、DMG通常速/CGB倍速。BGB 1.6.6とEmulicious 2026-03-27は既存ロックファイルの版・SHA-256で導入した。原作ゲームのデータを性能測定のために保存し直していない。

測定結果、ROM・状態・エンジンソースのハッシュは[集計JSON](stg-performance-investigation-results.json)。中間ROM、VRAM/OAMダンプ、参考ROMの局所逆アセンブル、画像はGit対象外の `.cache/stg-investigation/` にある。参考ROM本体や抽出したコード・画像をソースへ取り込んでいない。

| 検出したい問題 | 使用する計測 | 判断時の注意 |
|---|---|---|
| 本当のゲーム処理速度 | 更新入口の停止、CPU経過サイクル、PPUフレーム番号、公開済みOAM | ホストの処理時間や画面の59.7Hz表示をゲーム更新速度にしない |
| ホットスポット | `cpu-profile.mjs`：256～511 CPU T-cycle間隔を揺らしたPCサンプリング、CDB/MAP/NOIの関数帰属 | 割込み・待機も含む統計的推定。厳密な関数別実行時間ではない |
| 見えないコマ飛ばし | 1更新ごとの状態、弾座標、フェーズ、生成見送り数、転送済みOAMをシミュレーターと比較 | 完成したOAMをVBlank DMAで公開してから次の更新へ進む |
| 容量不足・表示欠け | 同時オブジェクト、OAM数、Y座標から計算した走査線別密度、生成見送り数 | 生成見送りと1走査線10個超過は別の現象 |
| 最適化による計算破壊 | 独立C計算と実際のSM83カーネルを診断ROM内で比較 | ホストからゲームRAMを書き換えて成功状態を作らない |

| エミュレーター依存の誤認 | BGBの公式headless・demo・breakpoint/watchpointログ | Boytaceanの観測と独立に照合する |

`stg-benchmark.mjs`は独立した検証用プロジェクトで実ROMを作る。高負荷は固定敵3機・8方向扇状弾、寿命384 tick、無敵時間1024 tick。各機種で720更新を検査し、120～720の600区間を集計する。32発の試験でも弾を生成する要求は上限を超えるため、生成見送りは184件ある。比較元24発は206件。同じ24発へ制限した現行エンジンでは、比較元と**両機種の状態/OAM連続ハッシュが完全一致**した。

通常戦闘はNOVA SPEARの元データでAを保持する。ボス試験だけはHPによるフェーズ遷移を180 tickの時間遷移へ変更し、3ボスの全フェーズを通す。これらの検証用変更を原作へ保存していない。

CIにも32発、12機、不均等アニメーション、全ボスとSM83比較試験を追加した。`--check-budget`で測定済み平均フレーム予算に余裕を持たせた退行検出を行う。60Hz達成を判定するゲートではない。

## GBの予算と、今回の原因

DMGは4.194304MHz、1画面70224 dots（154行×456）、約59.7275Hz。通常速では1画面17556 M-cycle、VBlankは4560 dotsに過ぎない。CGB倍速でもPPU/OAMの制限は増えない。[Pan Docs: Rendering](https://raw.githubusercontent.com/gbdev/pandocs/master/src/Rendering.md)

OAMは40個、8×8/8×16単位、1走査線では最初の10個までが選択される。Xだけ画面外へ隠してもYが重なると選択枠を消費する。DMAは160 M-cycleで、DMGでは640 dots。途中でOAMを差し替える多重化は可能だが、DMA中の表示と走査線境界の設計が必要になる。[OAM](https://raw.githubusercontent.com/gbdev/pandocs/master/src/OAM.md)、[OAM DMA](https://raw.githubusercontent.com/gbdev/pandocs/master/src/OAM_DMA_Transfer.md)

24発の変更前プロファイルでは、`step_entities`約20%、`sprite`約19%、`box`約16%で計55%、VBlank待機が約17%だった。NOVA SPEARでもスプライト準備、当たり判定の矩形生成、剰余が主要負荷だった。背景更新はこの測定区間の主因ではない。GBDKが生成したSM83コードでも、構造体・スタック経由の16bit値の読み直しと、座標変換が多いことを確認した。

GBDK公式の小さい整数、静的作業領域、少ない引数、前進ポインター、事前計算の指針を基礎に、生成アセンブリと実測で採否を判断した。Cをすべてアセンブラへ書き換えるだけでは、同じ計算の重複やOAM上限は解消しない。[GBDK Coding Guidelines](https://gbdk.org/docs/api/docs_coding_guidelines.html)

| 原因 | 実装した対策 | 維持した条件 |
|---|---|---|
| 弾にも25バイトの汎用構造体と複数の16bit演算を通す | 移動・年齢・寿命・画面外判定をSM83カーネルに集約 | Q4加算、16bit折返し、寿命・画面端の境界 |
| 敵弾ごとに4辺の矩形を作って自機と比較する | 素材ごとの相対中心区間を初期化時に計算。敵弾は中心で直接判定 | 元の矩形交差と等価。負の小数座標はゼロ方向へ丸める |
| スプライト座標・素材・OAM配置準備の費用 | 準備をSM83化し、1タイル弾は直接シャドウOAMへ出力 | 既存の複数タイル、HUDクリップ、描画順序、CGBパレット |
| 非均等アニメーションの剰余・フレーム走査が毎弾毎更新発生 | 安定したエンティティ枠ごとにフレームと残り時間を保持 | 2累乗の高速経路、枠再利用、点滅中の飛ばし、65535→0 |
| 内側ループのスタック参照 | 非再入の作業変数を静的化 | 割込みから更新・描画カーネルを呼ばない |
| プールの固定上限 | 敵12、敵弾32、総数39、5バイトの空きビット表 | OAM40個の生成時審査、自機弾6、ボス1、爆発4 |

構造体のサイズ・主要オフセットにはコンパイル時検査を置いた。SDCC/GBDKのレジスター引数規約を使用し、呼出し元のBC/DE/HLを保存する。任意のコンパイラーへの移植は未検証。

固定WRAM＋シャドウOAMは2046→2891バイト（+845）。速度の代わりに範囲表、アニメーションキャッシュ、増加枠を保持する。NOVA SPEARのROM容量は128KiBのままだが、固定ROMバンクの空きは748バイトで、今後のカーネル追加ではバンク配置が制約になる。

## 参考ROMで確認したこと

元ファイルは読み取りのみ。ローカルの解析コピーに対して、実行されたPCとバンクを確認してから局所逆アセンブルした。解析ツールは直接ストア命令の書込み試行を記録する簡易プローブで、全バスアクセスや全てのRAM実行コードを完全追跡するものではない。VRAMの実変化とBGBログを合わせて判断した。BoytaceanのLY値だけから実機の正確な書込みタイミングは断定していない。

### DANGAN v1.1

- SHA-256: `473bcc0291b42a763978640d3ad56a703587ed8c2327194a63434df604eb40fc`、256KiB、MBC1。
- 通常入力で戦闘へ進み、900フレーム後から120フレームを追跡。弾が多数ある画面でも、可視Y範囲のOAMは10～11個。BGマップの変更は少なく、BGタイル画像の書換えがある。
- 固定バンク`0516`以降に既描画部分のクリア、`0544`/`0548`等に既存VRAM値とのOR書込みがある。弾描画はBGタイルのピクセル操作と判断でき、ユーザーの仮説を裏付けた。
- `04B5`以降はX下位/上位、Y下位/上位、方向を`D000/D100/D200/D300/D400`に分けた配列へアクセスする。`INC D`/`INC H`で同じインデックスの別配列へ移る。速度表は`D800/D900`。汎用構造体のストライド計算を避けている。
- 弾ループの終端はインデックス`80h`。これは128枠の走査であり、128発が常時画面に出ているという意味ではない。
- `0449`の待機は`FF88 >= 3`を待ち、`0452`でリセットする。BGBで`02DA`のカウンター増加と弾ループ直前`04B2`を監視すると、連続119区間の平均は**2.99974表示フレーム、約19.91回/秒**。少なくともこの場面の弾移動は60回/秒ではない。音・自機・描画など全サブシステムの更新頻度が20Hzという意味でもない。
- BGパレットと2組の描画領域の交互使用もある。128枠、BG描画、更新頻度を組み合わせた設計であり、その一部だけをコピーして現エンジンの背景・色・更新仕様を維持できるとは限らない。

### 地球解放軍ジアース（提供されたMODRETRO版）

- SHA-256: `c7f0ef1bac33c1fecea47cb6b858e31c9c9abfc5d174865af13eb7668dbe3547`、128KiB、MBC1。
- 戦闘の120表示フレームで、固定バンク`0226`がLCDCへ`83h/8Bh`を交互に書く。bit 3が違うため、BGマップ`9800h/9C00h`を切り替えている。`0229`からSCYへ、それぞれの層に対応する異なる値を書き込む。
- BGBの独立したFF40/FF42監視でもPC・値の交互切替を確認した。ユーザーの多重スクロール仮説を、2つのBGマップと異なるスクロール値を時間的に交互表示する実装として裏付けられた。
- `0215`以降はRAM上のレジスター設定列からLCDC/SCY/SCX/WY/WX/LYCを反映する。画面全体のタイル画像を毎フレーム再転送する方式ではない。
- 調査場面のOAMは最大24個、最大4個/走査線。DANGANと同じ弾数を処理しているわけではなく、見た目の高度さからエンティティ処理性能を推定すべきではない。

## 次の設計変更の優先順位

1. **弾専用の配列構造と更新・描画の連結。** 次に大きく作り直す対象はここ。汎用25バイト構造体から位置・速度・寿命・素材だけを分け、ページ境界へ配置し、座標変換や走査の重複を減らす。DANGANの配列配置は参考になる。プール順序、自機弾の命中順、生成した更新では弾が動かない規則、保存/診断/シミュレーターとの整合性まで移行対象になる。今回の測定と等価性試験を受入条件にできる。
2. **表示上限への独立した方針。** 32発試験はOAM37個だが、最大22個/走査線なので欠ける。弾を優先するOAM選択、公平なローテーション、弾幕の走査線密度チェックが候補。ローテーションは欠けをちらつきへ変える手法で、全弾同時表示の解決ではない。衝突判定する弾が見えない問題を先に扱う必要がある。
3. **DMG専用のBG弾モードを分離して試作。** 多数の小さい単色弾を最優先し、背景タイル・スクロール・タイル枚数の自由度を制限できる作品向け。汎用BGと同居させる場合は、変更タイル管理、消去、地形復元、VRAM転送予算、色の制約が追加される。通常モードへの全面置換は現状の仕様を壊す。
4. **空間分割・ASM範囲拡張は再測定して選ぶ。** 自機弾6×敵/ボス最大13程度なら、格子管理の費用が利益を上回る可能性がある。今回高速化した敵弾対自機はそもそも1対N。残るホットスポットから順に対象を決め、C全廃を目的化しない。

ジアース式の交互BGは視覚表現として有効だが、弾の更新負荷の直接解決ではない。液晶での残像・ちらつき、CGB/DMGの色味は実機確認が必要になる。表示60Hzと弾更新20/30Hzを分ける設計も可能だが、既存作品の速度・操作感が変わるため今回は導入していない。
