# ロゴ後の音声付き動画 — 2026-09-17 調査

追記: v0.24で通常BG方式の短い音声付き動画をゲーム内へ統合する変更を行った。最新の形式・制限・検証方法は [startup-movie.md](startup-movie.md) を参照。以下はv0.23時点の比較調査であり、PV素材の試験結果と新しい入力動画の結果を混同しない。

## 結論

GB/GBCで事前変換した映像と音声を再生することは可能。MP4をROM内で直接デコードする方式ではない。今回のROM変更は展示ループであり、動画プレイヤーの統合はまだ行っていない。

GBCでは通常のBG方式（8x8タイルごとに4色、8パレット）に加え、走査線内のパレット更新を使う多色動画の先行実装がある。「フルカラー」が元動画の全RGB色を保持する意味なら不可だが、減色されたカラー動画を音声付きで見せる目的には実現例がある。

## 候補

| 方式 | 映像 | 音声 | 統合上の特徴 |
| --- | --- | --- | --- |
| GBC通常BG差分動画 | 160x144、タイル4色、ゲームと同じ7+1パレット規則を適用可能。初期試作は10〜15fpsを目標とするが未計測 | CH3へPCMを供給。まず低レートのモノラルを試作 | 既存画像変換を流用しやすい。全画面の二重バッファと転送予算が必要 |
| GBC専用多色動画 | GBVideoPlayer2の公称仕様は実効横120〜160、縦144、最大528色相当、29.86fps | 9198Hz、3bit、ステレオPCM | 画面とCPUのタイミングを専有する。既存の7+1パレット規則とは別の動画専用モード |
| DMG専用動画 | 4階調。解像度・差分量・fpsを落とした別データを用意 | 低ビットPCMのモノラルを検証 | GBCのDMAや多色プレイヤーをそのまま使えない。別の転送・音声ループが必要 |

GBVideoPlayer2の仕様・対応エミュレーター・ツールチェーンは作者の[README](https://github.com/LIJI32/GBVideoPlayer2/blob/master/README.md)に基づく。これは先行実装の能力であり、本エンジンで達成した実測値ではない。RGBDS製なのでSDCCオブジェクトとの直接混在は行わず、ライセンス確認のうえSDASへ移植するか、独立ビルドしたコードとデータの固定ABI・配置を検証する必要がある。

## エンジンへの挿入位置

`ロゴ → 動画（任意） → タイトル → 自動デモ → ランキング → ロゴ`。

1. 動画開始前にBGM、効果音、OAM転送、HUDのLCD割り込みを停止する。
2. CGB/DMGを判別し、専用に変換したデータを選ぶ。動画はROMバンクから読む。
3. 映像転送とPCM出力を単一の時間基準で同期する。ボタン入力は毎フレーム取得して中断できるようにする。
4. 完了・中断の両方でROM/VRAM/WRAMバンク、CPU速度、音源、割り込み、パレット、OAM、タイマーを復元する。
5. タイトル画像を読み直し、押しっぱなし入力が即ゲーム開始に流れないようにする。

動画中はゲーム処理を動かす必要がないため、専用プレイヤーに機械を明け渡せる。一方、GBVideoPlayer2の独立ROMが動くだけでは、この復帰経路の証明にはならない。

## 容量と転送の概算

通常BG方式の重複なし160x144画像は360タイル×16byte=5760byte。タイル番号360byte、GBC属性360byte、パレット64byteで約6544byte/フレーム。15fpsなら約98KB/s。4bit・8kHzモノラルPCMを仮定すると約4KB/sを追加する。15秒のGBC映像は圧縮前約1.53MBになる。DMG分は別途必要で、実際はタイル再利用・差分圧縮と映像内容によって変わる。この計算は容量の目安であり、転送速度の達成証明ではない。

MBC5の通常のROMアドレス範囲は最大8MiB。既存ゲームの占有量と、動画両機種分・再生コードを合わせて容量を決める。現在の銀行切替APIが8bitを使う箇所もあるため、4MiB超では9bit ROMバンクへの対応も監査する。

## 次の試作で確認すること

### 今回の素材試験

ユーザー指定により既存紹介PVの61〜75秒（14秒）を採用した。ナレーションの2文を切らず、フランドール戦とカットインを含む。ROM画面のゲーム領域を160x144へ切り出し、15fps・210フレームを既存の7パレット減色器で変換した。GB側も4階調へ変換した。最大ユニークタイル数は両版とも239だった。

`projects/touhou-kouma/touhou-kouma-design/video-v23/prepare.cjs` と `analysis.json` に手順とフレーム別計測を保存。`cgb-preview.mp4` / `dmg-preview.mp4` は画質評価用のPC動画であり、ROM再生の実測ではない。音声も8kHzモノラルへ落としたPCプレビューで、低ビットPCMハードウェア出力の再現ではない。元PVの仮Windowsナレーションを引き継ぐ。

239タイルは1画面分として収まるが、DMGで2画面分を同時に持つと478タイルになり、384タイル分の領域を超える。DMGは解像度縮小または差分更新が必要。GBCも単にメモリに収まるだけで転送・音声同期の成立を保証しない。

- 短い実素材で、GBC多色方式と通常BG方式の画質・容量を比較する。
- 通常BG方式は各タイル4色、ユニークタイル数、転送量をフレームごとに記録する。
- 動画→タイトル→ゲーム→動画を繰り返し、音声同期、中断、SRAM非破壊、状態復元を確認する。
- 高精度BGB/Emuliciousと実機で確認する。今回のBoytaceanによるゲーム検証を多色動画の動作保証には使わない。
