# アセットパイプライン

Caravan Editor作品は`assets-src/game.json`とPNGを原本に、共通ビルドで変換する実装になっています。正確なコマンド・インデックス順・美咲フォント抽出は[エディタ設計](caravan-editor-architecture.md)を参照してください。以下の一般例は非エディタ作品の拡張にも使用できます。

## 原則

人が編集する元データと、ツールが生成するデータを分離する。

```text
projects/<name>/assets-src/  ── 変換 ──▶  projects/<name>/generated/
          Gitで追跡                           原則Git追跡外
```

- PNG、曲データ、効果音定義、表計算などの原本は `assets-src` に置く。
- 生成されたC、H、BIN、タイルマップは `generated` に置き、手編集しない。
- 変換コマンド、入力、ツール版、オプション、出力名を再現可能にする。
- `generated/.gitkeep` だけを追跡し、生成物はビルド前処理で復元する。
- 元アセットごとに作者、出典、ライセンス、改変内容を記録する。

ツールの正確な版と配置は [`config/tools.lock.json`](../config/tools.lock.json) を参照する。版により変換結果やオプションが変わり得るため、ロック更新時は生成結果の差分を目視確認する。

## PNGからGBDKデータまで

標準の流れは次のとおり。

1. 8x8ピクセルのタイル境界を意識してPNGを作る。
2. DMGでも区別できる4段階の明度を基準にする。
3. CGB用の色は、同じ明度へ落としたときにも形が読めるよう選ぶ。
4. 背景、スプライト、UIを別ファイルまたは明確な領域へ分ける。
5. 固定済みGBDKに同梱された `png2asset` で変換する。
6. 生成物をコンパイルし、タイル数、ROM使用量、実画面を検証する。

`scripts` 配下へ置く変換スクリプトの最小形は次のようになる。実プロジェクトでは、固定された `png2asset` のヘルプと公式同梱例でオプションを確認し、ビルドスクリプトへ固定する。

```powershell
$root = (Resolve-Path "$PSScriptRoot\..").Path
$png2asset = Join-Path $root ".tools\gbdk\bin\png2asset.exe"
$input = Join-Path $root "projects\star-caravan\assets-src\sprites.png"
$output = Join-Path $root "projects\star-caravan\generated\sprites.c"
& $png2asset $input -o $output
if ($LASTEXITCODE -ne 0) { throw "png2asset failed: $LASTEXITCODE" }
```

スプライト幅・高さ、メタスプライト形式、タイル原点、パレット順などを指定する場合は、確認済みオプションをコマンドに明記する。開発者のGUI操作だけに依存する手順は採用しない。入力PNGが同じなら同じロック版と同じコマンドで同じ生成物になることを目標とする。

## Game Boy画像の基本制約

### 2bppと色

Game Boyのタイルは1ピクセルあたり2bitで、1パレットにつき4値を表す。DMGでは4段階の濃淡として表示される。通常のOBJ（スプライト）では色番号0が透明として扱われるため、見える色は実質3色で設計する。

CGBでは色そのものをパレットで指定できるが、タイルのピクセル値が4値である点は変わらない。DMG/GBC共通ROMでは、色差だけに意味を持たせず、明度、形、点滅、位置でも情報を区別する。

### 8x8タイル

- 背景とウィンドウは8x8タイルの組み合わせで作る。
- OBJは8x8または8x16モードで、モードは画面全体に影響する。
- 同一タイルを再利用し、VRAMとROMの重複を抑える。
- タイル番号の範囲を背景、UI、プレイヤー、敵などの所有者ごとに決める。
- 8x16 OBJでは上下のタイルペアとタイル番号規則を確認する。

### 背景とスプライト

背景へ置ける静的表現は背景タイルへ寄せ、動く物体や当たり判定が必要な物体をOBJへ割り当てる。OAMは40個、さらに1走査線上に表示できるOBJ数にも上限があるため、弾幕の見た目だけでスプライト予算を使い切らない。大きな敵はメタスプライトとして構成し、最悪時の同一走査線数を数える。

## パレットとインデックスの安定化

- PNGの自動減色へ無条件に任せず、使用色と透明色を意図的に管理する。
- スプライトの透明色が色番号0になることを変換後にも確認する。
- 同じ見た目でもパレット順が変わるとデータ差分が大きくなるため、順序を固定する。
- CGBパレットは視認性の補助として使い、DMG表示を壊さない。
- UI文字、敵弾、自機弾は背景と十分なコントラストを持たせる。

## 生成処理の設計

変換処理は、将来 `scripts/build.ps1` から呼び出すプロジェクト別スクリプト、または `project.json` の宣言として管理する。どちらの場合も次を満たす。

- 入出力パスはリポジトリルートから組み立て、空白を含むパスを引用する。
- `.tools` 内の実行ファイルを明示し、グローバルPATHへ依存しない。
- 出力先以外を削除しない。清掃前に対象がプロジェクト内の `generated` だと検証する。
- 変換失敗時は非0で停止し、古い生成物を成功結果として使わない。
- 可能なら一時ファイルへ生成してから置換する。
- 入力、コマンド、ツール版が変わった場合だけ再生成できるようにする。
- 生成物に元ファイル名や変換条件をコメントとして含める場合も、タイムスタンプなど非決定的情報は避ける。

`star-caravan` のサンプルが初期段階でCソース内の小さなタイル配列を使う場合も、規模を拡張する際は `assets-src` と `png2asset` の経路へ移す。生成ファイルを直接描き直す運用にはしない。

## 音楽と効果音

音楽ツールは初期環境の必須依存にしない。無音でも `bootstrap`、`doctor`、ビルド、テストが成立することを保つ。

将来hUGETrackerなどを追加する場合は、次の順序で導入する。

1. 公式配布元、安定版、ライセンス、Windowsでのポータブル利用可否を確認する。
2. 必要なら `config/tools.lock.json` にURLとSHA-256を固定する。
3. 編集可能な曲プロジェクトを `assets-src` へ置く。
4. 書き出し形式と変換コマンドをスクリプト化する。
5. ドライバーのCPU時間、ROM/RAM使用量、割り込みとの関係を計測する。
6. DMGとCGBの両方、および実機で音量とテンポを確認する。

書き出されたASMがRGBDS構文かSDAS構文かを確認し、異なるツールチェーンのオブジェクトを無検証で混在させない。必要ならデータのみを共通形式へ変換する。

## レビュー項目

アセットを変更したら、次を確認する。

- 元データとライセンス情報が追跡対象になっている。
- 生成物、ROM、ツール本体が追跡候補に入っていない。
- クリーン状態から変換とビルドを再現できる。
- タイル数とROM容量が意図せず増えていない。
- DMGの4階調で情報が判読できる。
- CGBパレットが適用され、ゲームロジックはDMGと同一である。
- BGBとEmuliciousで欠け、ちらつき、透明色の誤りがない。
