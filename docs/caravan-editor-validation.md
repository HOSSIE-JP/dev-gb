# 自動検証と受入確認

## テストの実行

標準のWindows環境では、リポジトリのルートで実行します。

```bat
doctor.cmd
test.cmd
build.cmd star-caravan -Configuration Release
build.cmd nova-spear -Configuration Release
```

エディターのみを検査する場合は`editor`で`npm run check`を実行します。`npm run test:core`はファイル管理・データ・編集処理、`npm run test:rom`はGBDKとBoytaceanを使うROM検査、`npm run test:bgb`はBGBのヘッドレス検査です。依存ツールがない場合、実行モードによって省略または失敗になります。ログの省略項目を成功件数に含めないでください。

## 自動検査の範囲

| 対象 | 確認内容 |
| --- | --- |
| 作品データ | ID、参照、画像寸法、色、タイル数、イベント範囲、パスの妥当性 |
| 保存・復旧 | 外部変更との競合、PNG往復、ジャーナル、破損復旧データ、書込み失敗 |
| ビルド | 固定版変換ツール、ROMヘッダー、バンク、成果物昇格、失敗時の保護、ROMハッシュ |
| エディター | ピクセル編集、Undo、入力解除、プレイヤーのフレーム予算、テンプレート継承 |
| 実ROM | DMG/CGBの入力・論理、VRAM/OAM、画面遷移、音声サンプル、スコア保存 |
| ファイル配布 | npmライセンス本文の収集、既知の実機起動ROMを含むWASMの書出し検査 |

短縮ステージや故障注入を使うテストは、個別機能の回帰検査です。通常の作品を最初から最後まで遊んだ結果とは区別します。テストの具体的な条件は`editor/tests`が正本です。

## 手動の受入確認

1. テンプレートから新規作品を作り、画像・敵・弾幕・ステージを編集する。
2. 保存してアプリを再起動し、変更が保持されることを確認する。
3. F5でビルドし、読み込まれたROMがその作品・ビルド構成と一致することを確認する。
4. DMGとCGBの両方で、タイトル・開始・ポーズ・被弾復帰・ボス撃破・ステージ切替・ゲーム終了を確認する。
5. ランキング更新後に再起動し、スコアが復元されることを確認する。
6. 全ステージを通常の条件で遊び、弾の視認性、混雑時の速度、音量、操作感を確認する。

BGB／Emuliciousでの確認は各ツールの利用条件に従います。実機では走査線制限、液晶上の視認性、入力、音声、電源再投入後の保存も確認します。

## 結果の記録

確認したコミット、ROMのSHA-256、ツールの版、機種、実行コマンド、成功・失敗・省略をPRまたはリリースの検証結果に記載してください。異なるROM版の測定値や全編クリア結果を引き継がないでください。

GitHub ActionsはWindowsのセットアップ、ビルド、テストを実行します。自動検査だけでWindows GUIの全操作や物理カートリッジの動作が保証されるわけではありません。
