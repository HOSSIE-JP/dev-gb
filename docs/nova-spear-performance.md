# Caravanランタイムの性能と測定

共通エンジンの最適化内容、24発の高負荷比較、再現手順は[STGエンジンの最適化と検証](stg-performance.md)を参照してください。

## 更新と描画

ゲームロジックはGBDK Cです。スプライトのOAMデータを生成する内側のループにはSM83アセンブラを使います。敵・弾・爆発は固定長プールを使用し、プレイ中に動的メモリ確保・解放を行いません。

1回の論理更新で作った表示をVBlankで転送してから、次の更新へ進みます。負荷が高いときは前の表示を保持してゲームの進行を遅くします。内蔵プレイヤーの通常速度も、遅れを取り戻すために表示フレームをまとめて実行しません。

GBCではCPU倍速を使います。同じ場面でもDMGとGBCの更新頻度は異なります。論理更新回数、エミュレーター表示フレーム数、ホスト側の描画回数を別々に扱ってください。

## 負荷が増える要因

- スプライトを構成するタイル数と、OAMへの書込み量。
- 敵・弾の移動、弾幕レイヤー、当たり判定の組合せ。
- 背景の更新、画面文字の更新、ステージ素材の読込み。
- VRAM/OAMを安全に扱うための待機と割込み。

オブジェクト生成数だけで原因を判断しないでください。生成見送りのカウンターはプール／OAM予算の不足を示し、描画フレームが省略された回数ではありません。1走査線10スプライトの上限による欠けもCPUの処理落ちとは別です。

HUDは変化した値を更新します。ボス撃破演出は戦闘オブジェクトを整理し、通常の敵AI・当たり判定を停止した状態で進めます。

## 測定用スクリプト

`editor/tests`には次の診断ツールがあります。各スクリプトの引数は冒頭の使用例を参照してください。

| スクリプト | 用途 |
| --- | --- |
| `performance.mjs` | 論理更新と表示フレームの進行を測定 |
| `spawn-performance.mjs` | 指定tick区間の生成・更新間隔を測定 |
| `profile-build.cjs` / `profile-runtime.mjs` | 一時的な計測ROMを作り、処理別の負荷を調べる |
| `publication-probe.mjs` | OAMの完成表示と更新の関係を観測 |

比較では、作品データ・入力・測定tick区間・機種・ツール版をそろえます。序盤、中盤の密集区間、各ボスを含め、平均と最大の更新間隔、サンプル数を記録してください。計測用ROMは通常の配布ROMと区別し、ROMハッシュも記録します。

変更を採用するのは、同条件で改善を確認し、実際のOAM表示とゲーム結果が保持される場合です。完成表示の転送待ちを削る、計測中だけ敵を減らす、表示されない更新を積み重ねる方法を性能改善として扱わないでください。
