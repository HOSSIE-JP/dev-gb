# デバッグガイド

## 基本方針

まずDebug構成で再現可能なROMを作り、BGBで短い反復確認を行い、必要に応じてEmuliciousでソース、メモリ、PPU、割り込みまで掘り下げる。エミュレーター間の挙動差があるため、片方だけの結果を実機の保証とはみなさない。

利用するツールの版と配置は [`config/tools.lock.json`](../config/tools.lock.json) を参照する。エミュレーターをシステムへインストールしたり、グローバルPATHへ追加したりする必要はない。

## Debugビルド

最初に環境を検査し、対象プロジェクトをDebug構成でビルドする。

```bat
doctor.cmd
build.cmd star-caravan -Configuration Debug
```

最小サンプルを使ってツールチェーンだけを切り分ける場合は次を実行する。

```bat
build.cmd hello-gb -Configuration Debug
```

Debug出力には、固定されたGBDK版で利用可能な範囲の `.noi`、`.sym`、`.map`、`.lst` などがROMと同じビルド領域に生成される。実際の出力名と配置はビルドログを正とし、Release出力をDebugセッションへ渡さない。

## BGB

BGBは、起動が軽く、ゲームプレイ、タイミング、ブレークポイント、逆アセンブル、メモリ、VRAM、OAMなどを素早く確認する用途に向く。

```bat
run.cmd star-caravan -Emulator BGB -Configuration Debug
```

確認の優先順位は次のとおり。

1. ROMが起動し、タイトルから全シーンへ遷移できるか。
2. DMG互換動作で表示崩れ、入力の取りこぼし、スプライト欠けがないか。
3. 2分タイマー、スコア、残機、ボス、クリア／ゲームオーバー条件が再現するか。
4. ブレークポイントやウォッチポイントで破損箇所を絞り込めるか。
5. フレームごとのCPU使用量とVBlank内の転送が過剰でないか。

BGB固有の設定やステートはローカルな実行データであり、Gitへコミットしない。

## Emulicious

Emuliciousは、Cソースとシンボルを関連付けた調査、CPUレジスタ、メモリ、VRAM、OAM、タイル、パレット、割り込みの詳細確認に使う。

```bat
run.cmd star-caravan -Emulator Emulicious -Configuration Debug
```

Javaが必要な配布構成では、リポジトリ内のポータブルJavaをラッパーが利用する。システムの `JAVA_HOME` を恒久変更しない。Javaが不要な配布構成なら、不要な環境変数を設定しない。

## VS Codeから使う

ポータブルVS Codeは次でリポジトリルートを開く。

```bat
vscode.cmd
```

タスク一覧から、まず `Doctor`、次に `Build star-caravan Debug` を実行する。`.vscode/launch.json` には、実際に導入したEmulicious Debugger 1.3.0の`package.json`で検証した起動構成がある。`Debug star-caravan in Emulicious`または`Debug hello-gb in Emulicious`を選ぶと、Debugビルド後にROMを起動し、既定ポート58870へ接続する。

`.vscode/launch.json` のキーを推測で追加しない。拡張の更新後に設定が変わった場合は、ポータブルVS Codeへ実際に導入された拡張のREADMEと `package.json` を確認して更新する。

## Cソースとシンボルが対応しないとき

次を上から順に確認する。

- `build.cmd ... -Configuration Debug` で作成したROMを開いているか。
- ROMと `.noi`、`.sym`、`.map` などが同じビルド実行から生成されたものか。
- `clean.cmd star-caravan` の後に再ビルドしても再現するか。
- デバッガーへ渡したパスが絶対パスで、空白を含むパスも正しく引用されているか。
- 最適化によって関数がインライン化・除去されたり、変数の生存期間が短くなったりしていないか。
- ROMバンキングを使う場合、ブレークポイントのアドレスだけでなく現在のROMバンクも一致しているか。
- 生成コードの行へ停止している場合、そのファイルが直近のアセット変換結果か。
- 固定ツール版とデバッガーが扱えるシンボル形式が一致しているか。

行単位の対応が不安定な箇所では、関数入口、既知のグローバル変数、ハードウェアレジスタへのアクセスを起点に逆アセンブルとソースを照合する。

## 重点的に見る領域

### VRAMとLCD

- LCD有効中のVRAM書き込みが安全な期間またはGBDKの安全なAPIを通っているか。
- 背景マップのタイル番号と、ロード済みタイルデータの範囲が一致しているか。
- DMGの濃淡とCGBのパレット番号を混同していないか。
- ウィンドウ座標やスクロール値がシーン切り替え後に残留していないか。

### OAMとスプライト

- OAMの40個上限を越えていないか。
- 1走査線に多数のスプライトが集中して欠けていないか。
- 非表示にしたいスプライトを画面外へ移動し、前シーンのOAMが残っていないか。
- 8x16モード使用時にタイル番号と上下ペアの規則を守っているか。

### メモリ

- 配列の添字が敵・弾・スコアテーブルの上限を越えていないか。
- 符号付き／符号なし8bit演算が意図せず折り返していないか。
- 大きなローカル配列や深い呼び出しでスタックを圧迫していないか。
- バンク切り替え後もポインタの参照先が有効か。

### CPUレジスタと割り込み

- 割り込み許可状態、`IE`、`IF`、`LY`、`STAT` を停止時点と合わせて確認する。
- VBlankを待つコードがLCD無効時や割り込み無効時に停止しないか。
- ISRが長すぎず、共有フラグ以外のゲームロジックを抱えていないか。
- ISRとメインで共有する値が `volatile` と明確な同期方針を持つか。

### Joypadとシーン

- 1フレームに複数回joypadを読み、エッジが不整合になっていないか。
- A/STARTの押しっぱなしが次シーンへ持ち越されて即決定になっていないか。
- ポーズ解除時にタイマーや敵更新が余分に1フレーム進んでいないか。

## DMG/GBC確認マトリクス

`star-caravan` は単一のDMG/GBC共通ROMである。最低限、BGBまたはEmuliciousの本体モードを切り替え、次を確認する。

| 項目 | DMGモード | CGBモード |
| --- | --- | --- |
| 起動と全シーン | 必須 | 必須 |
| 操作・当たり判定・タイマー | 同一結果 | 同一結果 |
| 表示 | 4階調で判読可能 | CGBパレットを適用 |
| スコア順位 | 上位5件をSRAMへ保存 | 上位5件をSRAMへ保存 |
| リセット後 | 保存済みスコアを復元 | 保存済みスコアを復元 |

最後に実機または信頼できるフラッシュカートで、画面端、入力、音量、電源投入時の初期状態を確認する。エミュレーターだけで実機タイミングや液晶上の見え方まで保証しない。
